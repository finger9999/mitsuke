# 미츠케 (Mitsuke) 설계 문서

Nov 14, 2026 · @낭연

## 개요

미츠케는 메루카리에 새로 올라온 매물 중 내 취향에 맞는 것만 골라 맥 알림으로 알려주고, Buyee로 바로 살 수 있게 연결해주는 개인용 직구 비서다. 이름은 일본어 "見つけ(찾았다)"에서 왔다.

| 항목 | 결정 |
| --- | --- |
| 검색 대상 | 메루카리 (직접 검색, 최신순) |
| 구매 경로 | Buyee (메루카리 공식 파트너, 결제와 해외 배송 대행) |
| 자동화 범위 | 구매 직전까지. 결제 버튼은 사람이 누른다 |
| 실행 환경 | 맥북 로컬, launchd로 1시간마다 실행 |
| 알림 | 90점 이상만 즉시 macOS 알림(클릭하면 Buyee 구매 페이지), 나머지 통과 매물은 메뉴바 목록에만 쌓임 |
| 개발 도구 | Python 파이프라인은 VS Code + Claude Code, 메뉴바 앱은 Xcode |

메루카리 직접 구매는 일본 휴대폰 번호와 결제 수단이 필요하고, 자동 결제는 계정 정지 위험이 커서 제외했다.

## 파이프라인

매물 하나는 싼 단계부터 비싼 단계 순서로 걸러진다. 비용이 드는 클라우드 LLM에는 애매한 매물만 간다.

```
launchd (1시간마다)
  │
  ├─ 1. 수집        메루카리 검색 (최신순)
  ├─ 2. 신규 감지   DB에 없는 매물 ID만 남김
  ├─ 3. 규칙 필터   가격·사이즈·제외 키워드          (공짜)
  ├─ 4. 임베딩 필터  ANE에서 사진 임베딩 → 취향 유사도  (온디바이스, 공짜)
  ├─ 5. LLM 채점   로컬 SLM(맥) → 그래도 애매하면 클라우드 LLM    (유료)
  ├─ 6. 가격 계산   상품가 + Buyee 수수료 + 예상 배송비 → 원화
  ├─ 7. 저장        SQLite
  └─ 8. 알림        90점 이상만 맥 알림, 나머지는 메뉴바 목록
                         │
                         ▼
            👍👎 피드백 ──► 평가셋 ──► 취향 기준 자동 개선 ──► 4·5단계에 반영

별도 창구: MCP 서버가 같은 DB를 에이전트에게 열어줌
```

- **첫 실행은 기준점만 저장**한다. 이미 올라와 있던 매물 수십 개가 한꺼번에 알림으로 오는 것을 막는다.
- **LLM 호출에는 실행당 상한**을 둔다. 상한을 넘거나 API가 실패한 매물은 점수 없이 메뉴바 목록에 올려서 놓치지 않는다.
- **검색어 사이에는 대기 시간**을 둔다. 한 번에 몰아서 요청하지 않는다.

## 폴더 구조

Python 파이프라인, Swift 앱, 평가, MCP 서버가 한 저장소에 있고 SQLite DB 하나를 공유한다.

```
mitsuke/
├── config.yaml              # 검색어, 예산, 취향 기준, 환율·배송 설정
├── main.py                  # run / recent / like / dislike / eval
│
├── finder/                  # 파이프라인 (Python)
│   ├── sources/
│   │   └── mercari.py       # 메루카리 검색 → 매물 목록
│   ├── filters.py           # 규칙 필터
│   ├── embed/
│   │   ├── model.py         # Core ML 모델 로드·추론 (ANE)
│   │   └── similarity.py    # 👍 매물과의 유사도
│   ├── scorer.py            # 클라우드 LLM 채점
│   ├── local_vlm.py         # 로컬 SLM 채점 (MLX/Core ML)
│   ├── tuner.py             # 피드백으로 취향 기준 자동 개선
│   ├── checkout/
│   │   └── buyee.py         # 메루카리 ID → Buyee 구매 URL
│   ├── pricing.py           # 원화 예상 총액
│   ├── store.py             # SQLite 읽기·쓰기
│   ├── notifier.py          # 맥 알림
│   └── pipeline.py          # 단계 연결
│
├── models/                  # 변환한 Core ML 모델 (.mlpackage)
│   └── convert.py           # PyTorch → Core ML 변환·양자화 스크립트
│
├── evals/
│   ├── datasets/            # 피드백으로 만든 정답셋 스냅샷
│   ├── run_eval.py          # 정밀도·재현율·비용 측정
│   ├── bench_ane.py         # CPU/GPU/ANE 속도·정확도 비교
│   └── reports/             # 실험 결과 기록
│
├── mcp_server/
│   └── server.py            # get_new_matches, give_feedback 등
│
├── app/MitsukeBar/          # SwiftUI 메뉴바 앱 (Xcode)
│
├── data/mitsuke.db
├── logs/
├── tests/fixtures/          # 저장해둔 메루카리 응답으로 파서 테스트
└── scripts/install_launchd.sh
```

`sources/`와 `checkout/`을 폴더로 둔 것은 나중에 라쿠마나 다른 대행사를 파일 하나 추가로 붙이기 위해서다. 대행사를 늘리면 그대로 루트별 최저가 비교가 된다.

## 모듈별 역할

각 모듈은 한 단계만 맡는다. 메루카리 페이지가 바뀌면 `mercari.py`만, LLM을 바꾸면 `scorer.py`만 고친다.

| 모듈 | 입력 | 출력 | 비고 |
| --- | --- | --- | --- |
| `sources/mercari.py` | 검색어 | 매물 목록 (ID, 제목, 가격, 이미지) | 제일 불확실한 부분이라 가장 먼저 확인 |
| `filters.py` | 매물 + 규칙 | 통과/탈락 + 이유 | 가격, 사이즈, 제외 키워드 |
| `embed/` | 매물 사진 | 취향 유사도 0\~1 | Core ML, Apple Neural Engine |
| `scorer.py` | 사진 + 제목 + 취향 기준 | 점수 0\~100 + 한 줄 이유 | 최근 피드백을 예시로 프롬프트에 넣음 |
| `local_vlm.py` | 사진 + 제목 + 취향 기준 | 점수 + 확신도 | 맥에서 실행, 확신도가 낮으면 scorer.py로 넘김 |
| `tuner.py` | 피드백 기록 | 새 취향 기준 초안 | 평가셋에서 점수가 오르면 반영 |
| `checkout/buyee.py` | 메루카리 ID | Buyee 상품 URL | `buyee.jp/mercari/item/{ID}` |
| `pricing.py` | 상품가, 카테고리 | 원화 예상 총액 | 배송비는 처음에 추정치, 실제 구매 기록으로 보정 |
| `store.py` | 매물, 점수, 피드백 | SQLite | Python과 Swift 앱의 유일한 연결고리 |
| `notifier.py` | 추천 매물 | 맥 알림 | 90점 이상만 알림, 클릭하면 Buyee 페이지 열림 |
| `mcp_server/` | 에이전트 요청 | 추천 목록, 피드백 기록 | DB 위에 얹기만 함 |
| `app/MitsukeBar/` | DB | 메뉴바 목록, 👍👎 기록 | 읽기 + 피드백 쓰기만 |

## 데이터 모델

테이블은 세 개로 시작한다. 핵심은 `listings`이고, 나머지는 임베딩 저장과 배송비 보정용이다.

**listings** (매물마다 한 줄)

| 컬럼 | 내용 |
| --- | --- |
| `id` | `mercari:m123...` |
| `search` | 어느 검색어에서 나왔는지 |
| `title`, `price_jpy`, `image_url`, `url` | 매물 정보 |
| `first_seen` | 처음 본 시각 |
| `status` | seeded / filtered / scored / notified |
| `filter_reason` | 규칙에서 탈락한 이유 |
| `similarity` | ANE 임베딩 유사도 |
| `score`, `score_reason` | 점수와 이유, 채점한 모델(로컬/클라우드), 호출 비용(USD) |
| `buyee_url`, `est_total_krw` | 구매 링크와 예상 총액 |
| `feedback` | 1 = 👍, -1 = 👎, 비어 있음 = 없음 |

**embeddings**: 매물 ID, 모델 이름, 벡터. 모델을 바꿔도 비교할 수 있게 모델별로 저장한다.

**purchases**: 실제로 산 매물의 예상 배송비와 실제 배송비. `pricing.py`의 추정치를 보정하는 데 쓴다.

## 포폴용 기술과 연결 방식

다섯 가지 기술이 하나의 흐름으로 이어진다. 포폴 한 줄 요약은 "엣지-클라우드 하이브리드 추론 파이프라인을 평가 기반으로 최적화했다"다.

| 순서 | 기술 | 붙는 곳 | 하는 일 | 포폴에 남는 숫자 |
| --- | --- | --- | --- | --- |
| 1 | 평가 하네스 + 비용 측정 | `scorer.py`, `evals/` | 👍👎를 정답 라벨로 쓰고, 프롬프트나 모델을 바꿀 때마다 정밀도·재현율과 함께 매물당 비용·월 예상 비용·LLM 호출 수를 한 줄로 비교 | 정밀도 개선폭, 매물당 비용 |
| 2 | 온디바이스 임베딩 (Core ML + ANE) | `embed/`, `models/` | CLIP 계열 모델을 Core ML로 변환·양자화하고 CPU, GPU, ANE에서 속도와 정확도 측정 | LLM 호출 절감률, 이미지당 추론 시간 |
| 3 | 로컬 소형 비전-언어 모델 (SLM) | `finder/local_vlm.py` | 임베딩을 통과한 매물을 맥에서 작은 비전-언어 모델로 먼저 채점하고, 확신도가 낮은 것만 클라우드 LLM으로 넘김. 양자화 수준별 품질·속도 비교 | 클라우드 호출 추가 절감률, 로컬 vs 클라우드 정밀도 차이 |
| 4 | MCP 서버 | `mcp_server/` | 추천 조회와 피드백을 에이전트 도구로 노출 | 사람용 화면과 에이전트용 인터페이스를 둘 다 설계 |
| 5 | 자기개선 루프 | `tuner.py` | 피드백으로 취향 기준을 고쳐 쓰고, 1번 평가셋에서 나아진 경우만 반영. 한국어 요청을 일본어 검색어로 확장하는 기능도 여기 | 기준 자동 개선 전후 정밀도 |

평가가 먼저인 이유: 2·3번에서 "정확도는 거의 그대로인데 비용이 줄었다"를 증명하려면 기준선이 있어야 한다. ANE는 맥에 들어 있는 NPU라서, 2·3번은 NPU 쪽 진로와 직접 연결된다.

## 로드맵

0단계만 끝나도 바로 쓸 수 있고, 이후 단계는 앞 단계의 데이터가 쌓여야 의미가 있다.

1. **0단계 · 기본 파이프라인**: `mercari.py` → 신규 감지 → 규칙 필터 → Buyee 링크 → 맥 알림. 아직 점수가 없으니 규칙을 통과한 매물은 모두 알림. launchd로 1시간마다 실행
2. **1단계 · LLM 채점 + 피드백**: `scorer.py`, 기본 pricing.py(카테고리별 고정 배송비 추정), CLI로 👍👎 기록. 이때부터 90점 알림 정책 적용
3. **2단계 · 메뉴바 앱**: SwiftUI로 목록과 👍👎를 앱에서 처리. 피드백이 편해야 평가용 라벨이 빨리 쌓이므로 평가 하네스보다 앞에 둔다
4. **3단계 · 평가 하네스**: 라벨 약 200개가 모이면 `evals/` 구축, 기준선 측정. 재현율을 재려면 규칙이나 점수에서 탈락한 매물도 일부 무작위로 뽑아 라벨을 단다
5. **4단계 · ANE 임베딩**: Core ML 변환·양자화, 벤치마크, 파이프라인에 끼워 넣기. 이어서 로컬 SLM을 붙여 클라우드 호출을 한 번 더 줄임
6. **5단계 · MCP 서버**
7. **6단계 · 자기개선 루프 + 가격 보정**: `tuner.py`, 실제 배송비로 `pricing.py` 보정
8. **이후 선택**: 아이폰 알림(서버 + 푸시), 대행사 추가해 루트별 최저가 비교

## 리스크와 원칙

- **메루카리 수집은 개인용 선을 지킨다.** 검색어 몇 개를 1시간 주기로만 돌리고, 공개 서비스로 키울 때는 수집 방식을 다시 정한다.
- **페이지 구조는 바뀐다.** 저장해둔 응답으로 파서 테스트를 돌리고, 매물이 0개면 로그에 경고를 남긴다.
- **결제는 자동화하지 않는다.** 잘못 산 건 되돌릴 수 없고, 자동 구매는 계정 정지 위험이 크다.
- **배송비는 추정치다.** 일본 창고에서 실측한 뒤 확정되므로, 알림에는 "예상"이라고 표시한다.
- **LLM 비용에는 상한이 있다.** 실행당 호출 수를 제한하고, API 키는 설정 파일이 아니라 환경 변수로 받는다.
- **맥이 꺼져 있으면 확인하지 못한다.** 초기에는 감수하고, 필요해지면 서버로 옮긴다.
